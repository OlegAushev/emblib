# Словарь объектов CANopen: constexpr-таблица и контекст обработчиков — план

Статус: план, работа не начата. Составлен 28 сентября 2026 года по итогам
обсуждения и прототипа. Прототип собран целиком в копии дерева (emblib и
adpt-etk-inverter), рабочее дерево при этом не менялось; все цифры раздела 3
получены на нём. Четыре решения ещё не приняты (раздел 4), от них зависят
шаги 1–3 плана.

Что меняется. Таблица словаря становится constexpr-объектом: строки
сортируются и проверяются при компиляции, а образ хранит их в `.rodata`.
Обработчики строк получают контекст — объект приложения, который держит
сервер, — и двухбайтовый аргумент своей строки. Строки параметров настроек
выводятся из схемы, как обещал §7 `settings-nvm-design.md`. API emblib
ломается, протокол на шине остаётся прежним.

## 1. Что сейчас

- `emb/can/canopen/od.hpp`: строка — это `od_entry {od_key, od_object}`. В
  `od_object` четыре `char const*` (категория, подкатегория, имя, единица),
  access, тип, `std::optional<od_value>` умолчания и два указателя, `read()` и
  `write(od_value)`, которым некуда передать контекст. На ARM строка занимает
  44 B.
- Таблица etk (`src/app/inverter/comm/can/canopen/od.cpp`, 165 строк) — это
  неконстантный `std::array`, потому что `sdo_server::init_dictionary()`
  сортирует её `std::sort` при старте. Поэтому она лежит в `.data`: 7 260 B
  RAM и столько же flash под образ инициализации. Дубликаты ключей ловит
  `assert`, то есть только в debug, других проверок нет.
- Обработчикам негде взять состояние. В od.cpp 9 вызовов
  `md::motor_drive::instance()`, есть `hall::angle_sensor::instance()` и
  `exists()`, extern-глобалы `dc_test::a/b/c`, которые читает server.cpp, и
  static-счётчики в пяти строковых обработчиках. Параметрам настроек нужна
  своя функция на каждого: 58 параметров дают 116 шаблонных thunk'ов
  `read_param<Name>`/`write_param<Name>`, 2.5 KB в release.
- 0x1011:04 (восстановить умолчание одного параметра) — особый ключ
  `sdo_server`: запись перехватывается до поиска по таблице. Строка 0x1011:04
  в таблице есть, но её writer никто не вызывает.
- `adpt-bike-inverter` устроен так же: 157 строк, 8 вызовов
  `motor_drive::instance()`, `hall::angle_sensor::instance()`/`exists()`,
  `dc_test`, те же счётчики и та же строка 0x1011:04.
- Хостовые таблицы (ucan-monitor, cannet) — отдельные копии метаданных без
  обработчиков, план их не трогает.

## 2. Дизайн

### 2.1 Типы

Новый заголовок `emb/can/canopen/dictionary.hpp`:

```cpp
using od_arg = std::uint16_t;

template<typename Ctx>
struct od_row {               // строка, как её пишет таблица
  od_key key;
  std::string_view category, subcategory, name, unit;
  od_access access;
  od_value_type type;
  std::optional<od_value> default_value = std::nullopt;
  od_read_result (*read)(Ctx&, od_arg) = nullptr;
  od_write_result (*write)(Ctx&, od_arg, od_value) = nullptr;
  od_arg arg = 0;
};

template<typename Ctx>
struct od_entry;              // строка в образе, 16 B:
                              // key, access, type, arg, read, write

template<auto const& Rows>
consteval auto make_dictionary();       // сортирует, проверяет,
                                        // возвращает dictionary<Ctx, N>
template<typename Ctx, std::size_t N>
class dictionary;                       // конструктор закрыт
template<typename Ctx>
class dictionary_view;                  // строится только из dictionary
```

Имена, единица и умолчание нужны проверкам и тому, кто читает исходник; в
образ они не попадают. `make_dictionary` — единственная дорога к
`dictionary`, а сервер принимает `dictionary_view`, так что несортированный
массив до поиска не доходит. Конструктор `dictionary_view` от rvalue надо
удалить: вид на временный словарь повиснет.

Таблица в приложении:

```cpp
constexpr row rows[] = {
  {{0x5000, 0x24}, "watch", "temp", "Tpwr_a", "°C", od_access::ro,
   od_value_type::float32, std::nullopt, Tpwr, nullptr, 0},
  setting<"drive.phase_swap">({0x3002, 0x01}, "config", "drive", "phase_swap", ""),
  // ...
};

constexpr auto dictionary = emb::can::canopen::make_dictionary<rows>();
```

### 2.2 Сервер

- `server<Opt, Ctx>` и `detail::sdo_server<NodeId, Ctx>`, конструктор
  `server(clock, bus, dictionary_view<Ctx>, Ctx)`. Сервер хранит `Ctx` по
  значению и отдаёт его через `context()`.
- Чтение вызывает `entry.read(ctx, entry.arg)`, запись —
  `entry.write(ctx, entry.arg, value)`. Строка читаема, если у неё есть
  reader, и записываема, если есть writer; после проверок это совпадает с
  access.
- `init_dictionary()` и собственный `find()` сервера уходят. Поиск — это
  `lower_bound` по отсортированным ключам в `dictionary_view::find()`.
- Особых ключей у сервера нет (если в вопросе 1 выбрано приложение).

### 2.3 Проверки

Общие проверки делает `make_dictionary`:

1. дубликат ключа;
2. пустые категория, подкатегория или имя;
3. дубликат тройки `категория/подкатегория/имя`: по ней строки ищут
   хост-утилиты;
4. access согласован с обработчиками в обе стороны. Ошибка — читаемая
   строка без reader'а, wo-строка с reader'ом, записываемая без writer'а и
   незаписываемая с writer'ом;
5. `exec` бывает только `wo`, `string` не записывается;
6. умолчание есть только у записываемой строки, и его альтернатива совпадает
   с типом строки.

Приложение проверяет свой массив `rows` (он constexpr, его можно обойти в
`static_assert`):

7. каждый параметр схемы с `expose` стоит ровно в одной строке настроек,
   параметр без `expose` — ни в одной.

Альтернативу, которую reader возвращает на самом деле, проверки не видят:
`od_value` её стирает. Эту дыру закрывают типизированные обработчики
(вопрос 2).

Ошибка выводится `static_assert` с текстом, собранным при компиляции (P2741,
GCC 14 и новее). Весь вывод занимает около 10 строк:

```
dictionary.hpp:247:27: error: static assertion failed: od: duplicate key 3002h:01: config/drive/phase_swap and config/drive/pwm_freq
```

Поэтому строки передаются аргументом шаблона (`template<auto const& Rows>`),
а не параметром consteval-конструктора: параметр функции не бывает
константным выражением, и `static_assert` по нему не написать. Массив строк
должен быть constexpr-объектом на уровне пространства имён: C-массивом или
`std::array`. Отвергнуто:

- `throw` в consteval (так устроен `cannet::canopen::dictionary` на хосте).
  Под `-fno-exceptions` он не компилируется вовсе: «exception handling
  disabled, use '-fexceptions' to enable».
- Вызов неопределённой функции (приём из `schema.hpp`). С именованной
  таблицей ошибка короткая, но не называет строку. Если же передать таблицу
  фигурными скобками, GCC печатает её целиком в контексте вычисления: одна
  строка в 341 KB на 165 строк таблицы.

### 2.4 Контекст

- У сервера один объект `Ctx`, у каждой строки — compile-time `od_arg`.
  Обработчик получает `(Ctx&, od_arg)`.
- Указатель на объект в каждой строке невозможен: объекты в `main()`
  автоматические, их адреса — не константы. А таблица, которую дописывают при
  старте, уже не constexpr.
- `Ctx` — параметр шаблона, а не `void*`: так не нужны приведения, а
  инстанцирование на приложение всё равно одно.
- `od_arg` — это `std::uint16_t` в padding после типа, строку он не
  увеличивает. Им пользуются 58 строк настроек (индекс параметра: одна пара
  `read_setting`/`write_setting` вместо 116 thunk'ов), `Tpwr`, `Tmot`, `Vext`
  (номер датчика), `logger` (номер канала), а если счётчики переедут в
  контекст — и строковые обработчики (номер строки).
- Контекст etk в прототипе:

  ```cpp
  struct context {
    md::motor_drive& drive;
    hall::angle_sensor* hall;  // nullptr, если датчика Холла нет
    duty_cycles dc_test{};
  };
  ```

  `main()` передаёт в него `{.drive = drive, .hall =
  std::get_if<hall::angle_sensor>(&angle_sensor)}`, а server.cpp читает
  `server_.context().dc_test`. Глобальными остаются `telemetry`, `settings`,
  `trouble`, планировщик и `sysinfo` (вопрос 4).

### 2.5 Строки настроек

```cpp
setting<"drive.phase_swap">({0x3002, 0x01}, "config", "drive", "phase_swap", ""),
```

`setting<Name>` берёт из `settings::parameter<Name>` тип (альтернативу
`to_od_value(default)`), умолчание и индекс, который кладёт в `arg`. Access
тоже выводится: `rw`, если параметр `writable`, иначе `ro` без writer'а. Имя
параметра пишется один раз вместо трёх, а тип и умолчание не могут
разойтись со схемой. Индексы OD по-прежнему задаются руками: это внешний
контракт (§7 design-doc'а).

### 2.6 Восстановление одного умолчания (0x1011:04)

В прототипе это обычная строка приложения. Её writer раскладывает `uint32`
в `od_key` так же, как прежний `memcpy`: индекс — младшие 16 бит, подындекс —
следующие 8. Затем он находит строку через `object_dictionary.find()` и для
строки настроек вызывает `settings::restore_default_at(entry.arg)`. Строку
настроек он узнаёт по `entry.write == write_setting`.

Коды ошибок остались прежними: нет ключа — `object_not_found`, строка не
записывается — `write_to_read_only`, у строки нет умолчания —
`no_data_available`. Умолчания в образе не нужны. Альтернатива описана в
вопросе 1.

## 3. Результаты прототипа (2026-09-28)

База — app `f870bef` и emblib `fcf9b78`. Прототип — база плюс всё из
раздела 2, кроме типизированных обработчиков; счётчики строк остались
static. FLASH считается как сумма `.apm32_isr_vector`, `.text`, `.rodata`,
`.ARM`, `.init_array`, `.fini_array` и `.data`. RAM здесь статическая:
`.data` + `.bss`.

| Пресет | FLASH до | FLASH после | Δ FLASH | Δ RAM |
|---|---:|---:|---:|---:|
| rev-a-release | 107 500 | 95 456 | −12 044 | −7 276 |
| rev-a-debug | 434 160 | 419 436 | −14 724 | −7 276 |
| miniboard-release | 105 804 | 93 676 | −12 128 | −7 276 |
| miniboard-debug | 426 164 | 411 740 | −14 424 | −7 276 |

Откуда разница в rev-a-release. Разбивка по `nm`, выравнивание не учтено,
поэтому сумма не сходится с итогом байт в байт:

| Что | FLASH | RAM |
|---|---:|---:|
| Таблица: `.data` 7 260 → `.rodata` 2 640 (44 → 16 B на строку) | −4 620 | −7 260 |
| Имена, единицы и категории больше не в `.rodata` | ≈ −1 860 | |
| `std::sort` и `init_dictionary()` при старте | −2 680 | |
| 116 thunk'ов настроек | −2 552 | |
| `logger_ch0..9` → `logger`; `Tpwr<I>`, `Tmot<I>`, `Vext<I>` → функции с `arg` | ≈ −770 | |
| 0x1011:04 (см. ниже) | +136 | |
| Конструирование контекста в `main` | +124 | |

Строка 0x1011:04 складывается так: `try_handle` −224, writer в приложении
+184, `settings::restore_default_at`, впервые попавший в образ, +204, старый
мёртвый writer −28.

Размер читателей не изменился (`Vdc` 24 B и до, и после). Писатели те же или
до 20 B меньше: вместо загрузки синглтона у них ссылка на привод. od.cpp
компилируется 3.6 → 4.0 s, пиковая память компилятора выросла с 362 до
403 MB.

Проверено:

- все 4 пресета собираются с `-Werror` без предупреждений;
- на сегодняшней таблице проходят проверки 1–7: все 58 параметров схемы
  имеют `expose` и стоят каждый ровно в одной строке;
- все 58 типов, выведенных из схемы, совпали с написанными в таблице руками
  (временные `static_assert`);
- в таблицу вносилось по одной ошибке на проверки 1, 3, 4 и 6, и каждая
  давала одну строку сообщения с ключом и именем строки;
- имён строк в `.rodata` образа больше нет;
- по коду на шине ничего не меняется: ключи, типы, access и коды ошибок
  0x1011:04 прежние. На железе не проверялось;
- типизированный обработчик за шаблонным thunk'ом (вопрос 2) даёт тот же
  код: `read_thunk<&Vdc_typed>` — 24 B, те же инструкции, что у `Vdc`, а
  `write_thunk<&set_pwm_freq_typed>` — 240 B, как `set_pwm_freq`.

## 4. Открытые вопросы

1. **Где восстанавливать умолчание (0x1011:04).** В прототипе — в
   приложении (2.6): у сервера нет особых ключей, умолчаний в образе нет.
   Смущает только то, что строку настроек writer узнаёт по адресу
   `write_setting`. Если оставить восстановление в сервере, умолчания нужны
   в образе. Это либо отдельная отсортированная таблица `{od_key, 4 байта}`
   только для строк с умолчанием (58 × 8 = 464 B), либо
   `std::optional<od_value>` в каждой строке (28 B вместо 16, +1 980 B).
2. **Типизированные обработчики — сразу или вторым шагом.** Обработчик
   выглядит как `float Vdc(context&)`, строка — как
   `od::ro<Vdc>({0x5000, 0x11}, "watch", "elec", "Vdc", "V")`. Тип строки
   выводится из сигнатуры, access — из имени построителя, из писателей
   уходят `get_if` с `general_error`, а reader больше не может вернуть не тот
   тип. В release код тот же (раздел 3). Debug собирается с `-O0`, там на
   каждый обработчик прибавится вызов.
3. **Где живёт `setting<>`.** В прототипе — в od.cpp etk. Bike нужен такой
   же, поэтому в emblib ему место в `od_settings.hpp` из §7: шаблоном по
   схеме и паре обработчиков.
4. **Сколько положить в контекст.** Только объекты из `main()`, как в
   прототипе, или сразу ещё `telemetry`/`settings`/`trouble`. API сервера от
   этого не зависит, сервисы можно перенести и позже.

Кроме того, прототип принял решения, которые можно пересмотреть:

- имена в образ не попадают; если на плате понадобится их печатать, можно
  вернуть флагом;
- access хранится в строке, хотя после проверок он следует из обработчиков:
  место под него всё равно свободно;
- сервер хранит `Ctx` по значению (контекст из ссылок это позволяет);
- `od_arg` двухбайтовый.

## 5. План работ

Коммиты идут в обычном порядке: emblib, затем etk с бампом emblib в том же
коммите, затем bike.

1. **emblib.**
   - `emb/can/canopen/dictionary.hpp`: `od_arg`, `od_row`, `od_entry`,
     `detail::od_verdict`, `detail::sorted`, `detail::check`,
     `make_dictionary`, `dictionary`, `dictionary_view` (без конструктора от
     rvalue).
   - `od.hpp`: убрать `od_object`, `od_entry`, операторы сравнения,
     `od_no_read`/`od_no_write` и `od_read_var`/`od_write_var` (последние
     никто не использует). `od_key` получает `==` и `<=>` по умолчанию.
   - `detail/sdo_server.hpp`, `server.hpp`: параметр `Ctx`, конструктор с
     `dictionary_view<Ctx>` и `Ctx`, метод `context()`. Убрать
     `init_dictionary()`, собственный `find()` и, в зависимости от вопроса 1,
     перехват 0x1011:04.
   - Тест `emb/test/canopen_dictionary_test.cpp`: `static_assert` над
     маленькими таблицами. Каждая проверка срабатывает со своим текстом,
     правильная таблица проходит, порядок после сортировки верный, `find()`
     находит строки.
   - В зависимости от вопроса 3 — `od_settings.hpp`.
   - `settings-nvm-design.md` §7: обновить статус.
2. **etk.**
   - `od.hpp`: `context` и `extern dictionary_view<context> const
     object_dictionary`.
   - `od.cpp`:
     - сигнатуры обработчиков → `(context&, od_arg[, od_value])`;
       синглтоны и `dc_test` переезжают в контекст;
     - `Tpwr`, `Tmot`, `Vext` и `logger` становятся одной функцией каждый,
       с `arg`;
     - `read_setting`/`write_setting` и `setting<>` вместо
       `read_param`/`write_param` с `[[gnu::noinline]]`;
     - 0x1011:04 — в зависимости от вопроса 1;
     - таблица конвертируется по правилам раздела 7 и строится через
       `make_dictionary<rows>()`;
     - `static_assert` полноты (проверка 7) остаётся навсегда.
   - Счётчики строк можно перенести в контекст (курсор на строку, номер
     строки в `arg`). На размер это не влияет.
   - `server.hpp`/`server.cpp`: `server<opts, od::context>`, конструктор с
     видом и контекстом, `make_run_command()` читает
     `server_.context().dc_test`. `main.cpp` конструирует контекст.
   - Проверка: 4 пресета; размеры против раздела 3; дифф `nm`. Временный
     `static_assert` на совпадение 58 типов со старой таблицей перед
     коммитом убрать.
3. **Типизированные обработчики** — если по вопросу 2 решено их делать.
   Построители `od::ro/wo/rw/constant/exec<F>` в emblib, обработчики etk
   возвращают `T`; проверить, что release не изменился.
4. **bike.** Те же изменения по тем же правилам: 157 строк, 8
   `motor_drive::instance()`, `hall::angle_sensor::instance()`/`exists()`,
   `dc_test`, счётчики, строка 0x1011:04; бамп emblib.
5. **Стенд (ucan-monitor).**
   - прочитать все строки watch, config и info, строковые — до конца;
   - записать параметр config и прочитать его обратно;
   - 0x1011:04: для параметра настроек возвращается умолчание, для строки
     без умолчания — ответ `0x08000024`, для несуществующего ключа —
     `0x06020000`;
   - чтение wo-строки даёт `0x06010001`, запись в ro — `0x06010002`;
   - exec-команды 0x1010:01, 0x1011:01/03, 0x2001:01/02 работают как раньше,
     включая отказ `0x08000022`, когда привод не стоит.

## 6. Подводные камни

- A/B делать в двух копиях дерева с путями одинаковой длины: debug кладёт
  `__FILE__` в `.rodata`. Сравнивать секции, а не итог `size`:
  git-version-tracking кладёт в образ тему коммита.
- `make_dictionary` возвращает словарь по значению, поэтому
  `constexpr auto dictionary = make_dictionary<rows>();` должен стоять на
  уровне пространства имён. Наружу отдаётся
  `constinit dictionary_view<context> const`, как в прототипе.
- Writer 0x1011:04 в прототипе берёт `std::get<std::uint32_t>`. С
  `-fno-exceptions` неверная альтернатива завершила бы программу. Для `exec`
  альтернатива всегда `uint32`, но `get_if` надёжнее.
- Хостовые утилиты менять не нужно. Порядок строк в `rows` прежний, но
  формат строки другой, так что построчное сравнение с копией в ucan-monitor
  станет шумнее.

## 7. Как конвертировать таблицу

Прототип конвертировал таблицу скриптом по таким правилам:

- `{{I, S}, {"кат", "подкат", "имя", "ед", od_access::A,
  od_value_type::T, D, R, W}},` → `{{I, S}, "кат", "подкат", "имя", "ед",
  od_access::A, od_value_type::T, D, R', W', arg},`;
- `emb::can::canopen::od_no_read` и `od_no_write` → `nullptr`;
- строка с `read_param<"x">`/`write_param<"x">` → `setting<"x">({I, S},
  "кат", "подкат", "имя", "ед")`: тип, умолчание и access берутся из схемы;
- `Tpwr<N>`, `Tmot<N>`, `Vext<N>` → имя функции и `arg = N`,
  `logger_chN` → `logger` и `arg = N`, у остальных `arg = 0`;
- сигнатуры: `od_read_result f()` → `od_read_result f(context&, od_arg)`,
  `od_write_result f(od_value[ val])` → `od_write_result f(context&, od_arg,
  od_value[ val])`. Шаблонные читатели и thunk'и настроек нужно переписать
  раньше общей замены сигнатур, иначе она заденет и их.
